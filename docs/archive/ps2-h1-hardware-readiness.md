# H1: Real-PS2 hardware readiness and diagnostics

**Date:** 2026-10-22

**Target:** European PS2 Slim SCPH-7500x via wLaunchELF and USB.

**Related:**
- [ps2-p3-report.md](ps2-p3-report.md)
- [ps2-hardware-first-boot.md](ps2-hardware-first-boot.md) (printable checklist)
- [ps2-usb-readme.txt](../ps2-usb-readme.txt) (the README on the stick)

> **No physical PS2 was used.** Everything marked [M] was measured in PCSX2 v2.8.2 (BIOS SCPH-75001 v2.20, NTSC).
>
> PCSX2 does **not** validate:
> - USB mass-storage compatibility: PCSX2 has no USB storage, so the build runs from its `host:` filesystem;
> - real EE timing or caches;
> - SPU2 audio output;
> - CRT display or PAL-console behaviour.
>
> Those items are listed in §10 as hardware-only.

## Summary of what H1 adds

| Area | What | Where |
|---|---|---|
| Start-up screen | Text "boot console" (ps2sdk libdebug) listing each start-up stage from the IOP reset onwards, until the renderer takes over | `src/PS2Diag.cpp`; hook in SDL's PS2 `main()` (SDL patch 0007) |
| Fatal errors | `VVV_exit(≠0)` shows a FATAL ERROR screen (reason, last stage, last 6 errors/warnings, log path) and stays there | `PS2Diag_Fatal`, `main.cpp` |

| Error capture | Every `vlog_error`/`vlog_warn`/`vlog_info` goes to `vvvvvv_ps2.log`. Errors/warnings feed the fatal screen and the overlay. `SDL_assert` failures are logged and shown instead of ending the program | `Vlogging.c`, `PS2Platform.cpp` |

| Hardware benchmark | `bench.txt` with `preset=hardware`: six P3 scenes, no input; per-scene TPS (mean and minimum over 1 s windows), frame mean/P95/P99/max, render time, underruns, memory → `bench_results.txt` | `PS2Bench.cpp` |
| Storage self-test | `fs_smoke.elf` now also re-reads 29 regions (5 whole files incl. `VVVVVV.elf`, 24 chunks across `data-ps2.zip`) and compares CRC32s; repeats failed checks at the end | `tests/ps2/fs_smoke/` |
| Packaging | Checks the input `data.zip` has all 49 assets the game loads; writes `fs_smoke_expect.txt` and `optional/{bench,overlay}.txt` | `scripts/make-usb-package.sh` |

## 1. USB directory structure

Generated by `scripts/make-usb-package.sh`. Copy the whole `VVVVVV` folder to the **root** of a FAT32 stick:

```
<stick root>/
└── VVVVVV/
    ├── fs_smoke.elf          storage self-test (run first)
    ├── VVVVVV.elf            the game (stripped, ~5.8 MB)
    ├── VVVVVV-nomusic.elf    the game without music (fallback)
    ├── data-ps2.zip          your data.zip, music blob stored (~63.4 MB)
    ├── fs_smoke_expect.txt   CRC32s re-checked by fs_smoke.elf
    ├── MANIFEST.sha256       SHA-256 of every file (check on a PC)
    ├── README-PS2.txt        on-stick instructions
    ├── SOURCE.txt            source versions + hashes of the unstripped ELFs
    ├── lang/en/…             game text (from the VVVVVV repo)
    ├── fonts/…               font.png, button glyphs
    └── optional/
        ├── bench.txt         copy into VVVVVV/ to run the benchmark
        └── overlay.txt       copy into VVVVVV/ to start with the overlay on
```

**Created by the game at run time** (next to the ELF):
- `vvvvvv_ps2.log`;
- `savedata/` (`saves/settings.vvv`, `unlock.vvv`, …);
- `bench_results.txt`, `bench_NN_*.csv`, `prof_NN_*.txt` and `golden_NN_*.ppm` (benchmark only).

`fs_smoke.elf` creates `fs_smoke.log` and a temporary file in `savedata/`, which it deletes.

All paths are relative to the ELF's directory. The game takes its base directory from `getcwd()`, which ps2sdk sets from `argv[0]`, so the folder name and the device prefix (`mass:`, `mass0:`) do not matter [C].

## 2. Launch `fs_smoke.elf` (wLaunchELF)

1. Insert the stick in a front USB port, then start wLaunchELF.
2. **FileBrowser** → `mass:/` → `VVVVVV/` → `fs_smoke.elf` (✕ / ○ depending on your wLaunchELF setup).
3. The text screen shows:
   - argv/cwd;
   - device-ready time;
   - the folder listing (first 8 entries);
   - presence of the required files;
   - the zip method of the music blob;
   - sequential and random read timings;
   - **CRC32 checks of 29 regions**;
   - savedata write/read/delete.

   It ends with `ALL OK`, or with `PROBLEMS` plus a list of the failed checks. The 40-line screen wraps, so failures are repeated at the end.
4. Photograph it and reset the console. `fs_smoke.log` is in the folder.

## 3. Launch VVVVVV

**FileBrowser** → `mass:/VVVVVV/VVVVVV.elf`. The expected start-up messages are in §6.

The title screen should follow, and from there the game works as in PCSX2:
- ✕ flip/confirm;
- ○ back/pause menu;
- △ map;
- □ interact;
- R1 restart.

`VVVVVV-nomusic.elf` is the same game without music. Use it to tell music-streaming problems from everything else.

## 4. Diagnostic overlay

**Toggle:** press **L3 + R3** (both sticks) together. VVVVVV binds neither stick click by default. To have it on from the start, copy `optional/overlay.txt` next to the ELF.

```
TPS 29.3/29.4 FRAME 34.1ms RND 14.7ms        ← logic ticks/s actual/target, loop period, render time
MUSIC on  107ms/s UNDERRUN 0 FREE 6.4M        ← music decode time per second, total underruns, free memory
STATUS OK  L3+R3 hides this                   ← or "ERR <last error/warning>", or benchmark status
```

**Layout:** 320×32 at y=16 (below the top CRT overscan), white or coloured on black, 8×8 game font.
- Line 1 turns pink when TPS is more than 0.5 below target.
- Line 2 turns pink once any underrun has happened.

**Cost.** The text is redrawn once a second, into a small texture with about 120 glyph blits. Each frame costs one unblended 320×32 copy onto the finished window, which is a row `memcpy` on the P3 fast path. No allocation after the first use; values are formatted with `snprintf` once a second.

**Measured overhead** [M] (`preset=hardware`, overlay off vs on, same ELF):

| scene | render ms (off → on) | TPS (off → on) |
|---|---|---|
| intro_dialogue | 10.78 → 11.01 | 29.4 → 29.4 |
| room_ss1 | 14.84 → 14.99 | 29.2 → 29.3 |
| tower | 23.61 → 23.96 | 25.0 → 24.9 |
| tower_climb | 21.24 → 21.57 | 28.9 → 28.9 |
| panic_room | 24.20 → 24.45 | 25.1 → 24.9 |
| super_gravitron | 20.76 → 21.06 | 29.2 → 29.3 |

Render time rises by 0.2–0.4 ms (1–2%). TPS is unchanged within noise (worst-case towers 25.0/25.1 → 24.9).

The overlay is drawn on the window after the frame, so it does not appear in the golden frames (`gameTexture`) and does not change game rendering.

## 5. Deterministic hardware benchmark

1. Copy `optional/bench.txt` (contents: `preset=hardware`) into `VVVVVV/`.
2. Start `VVVVVV.elf`. **No input is needed.**

**What happens:**
1. 300 logic ticks after the title appears:
   - a golden-frame pass: 6 scenes × 90 ticks, a few seconds;
   - then **6 measured scenes**, each with 4 s settle (+5 s for time-trial countdowns) and **20 s measured**.
2. Total about 4 minutes [M: 3.6 min in PCSX2, including boot].
3. The overlay then appears with `BENCH DONE: see bench_results.txt`. Reset the console, and delete `bench.txt` to play normally.

**Scenes:** these are P3's scenes, reached with the game's own entry points, with an unchanged workload.

| scene | what |
|---|---|
| intro_dialogue | dialogue-heavy (new-game intro text box) |
| room_ss1 | normal room (Space Station 1 time trial) |
| tower_climb | the Tower, player keeping up with the camera (typical) |
| tower | the Tower, player falling behind (worst case: full background redraw every tick) |
| panic_room | Panic Room minitower (worst case, as above) |
| super_gravitron | Super Gravitron |

**Results.**
- `bench_results.txt` is collected in RAM and written once at the end.
- Per-scene CSVs, profiles and golden PPMs are written *between* scenes, outside the measured windows.
- Columns: TPS mean and `tps_min` (slowest 1 s window); loop period mean, P95, P99 and max (ms); render mean (ms); underruns during the scene; `malloc_in_use` (MiB).

PCSX2 reference [M]:

```
# VVVVVV PS2 benchmark: settle=4 s measure=20 s over30=-1 opts=0xffffffff overlay=0
# times in ms; tps = logic ticks per second (full speed 29.4); tps_min = slowest 1 s window
# scene            tps   tps_min frame  p95    p99    max    render underruns mem_MiB
intro_dialogue     29.4   29.3  34.02  34.40  34.69  35.01  10.78      0   17.22
room_ss1           29.2   29.1  34.21  35.70  36.76  37.34  14.84      0   17.21
tower              25.0   25.0  39.93  43.15  46.06  47.80  23.61      0   17.21
tower_climb        28.9   28.3  34.55  38.43  40.58  42.70  21.24      0   17.21
panic_room         25.1   24.8  39.83  43.75  46.07  48.46  24.20      0   17.21
super_gravitron    29.2   29.1  34.23  35.65  37.16  37.47  20.76      0   17.21
```

**Comparing PCSX2 and hardware:**
- Put the console's `bench_results.txt` next to this table.
- The `GOLDEN … crc32=` lines in `vvvvvv_ps2.log` should match PCSX2's if the console computes the same frames. A mismatch would point at EE FPU or timing differences, not necessarily a bug.
- The other benchmark options from P3 still work: `scenes=`, `measure=`, `opts=0`, `over30=`, `profile=`, `golden=`, `overlay=1`.

## 6. Expected start-up messages

On the boot console (white on black; grey for steps before the game's code runs):

```
VVVVVV for PlayStation 2 - experimental test build
start-up (the title screen replaces this text):

IOP reset
loading IOP drivers (USB, memory card, HDD, CD)
waiting for the boot device
boot device ready
boot device mass:/VVVVVV/, real storage                ← host:/ … host storage in PCSX2
assets archive: mass:/VVVVVV/data-ps2.zip
filesystem ready
SDL started: video PS2, audio ps2, N controller(s)
settings loaded; starting the renderer (this text disappears)
```

**After that** the game's renderer takes the screen. The log continues with:
- `renderer ready`;
- `loading graphics, sounds and music`;
- `resources loaded, entering the main loop`;
- `MILESTONE first frame presented`.

Verified in PCSX2 [M], captured with `bootshot.txt`; the boot device line reads `host:/`.

**Not verifiable in PCSX2:**
- how long "waiting for the boot device" takes on a real stick;
- the exact device prefix wLaunchELF passes (`mass:` vs `mass0:`).

## 7. Troubleshooting

| Symptom | Likely cause | What to do |
|---|---|---|
| wLaunchELF error when starting the ELF | Corrupt copy, or wLaunchELF cannot read the stick | `sha256sum -c MANIFEST.sha256` on the PC; try another stick or port; run `fs_smoke.elf` |
| **Black screen, no text at all** | Hang before the first message (ELF not running, or video not switching). The console's video signal/cable (NTSC 60 Hz) | Check that wLaunchELF's own screen is visible on this TV/cable. Try RGB SCART or component. Note how long you waited |
| Text stops at `waiting for the boot device` / shows `boot device NOT ready` | USB driver does not see the stick | Other stick (smaller, older, FAT32, MBR), other port. Run `fs_smoke.elf` |
| FATAL ERROR: `data.zip missing` / `PS2: put data-ps2.zip …` | Archive missing or not next to the ELF | Re-copy the package folder; the path is printed on screen |
| Text stops after `SDL started` or `starting the renderer` | Renderer/GS initialisation problem | Photograph; send `vvvvvv_ps2.log` |
| CPU EXCEPTION screen | Crash | Photograph (EPC/RA); symbolise with `scripts/ps2-profile.py out/vvvvvv-ps2/VVVVVV.elf --addr <EPC> <RA>` |
| Game runs, no music | Music streaming problem, or archive repacked wrongly | Overlay: `MUSIC off`/underruns; log lines `Music: …`; compare with `VVVVVV-nomusic.elf` |
| Music stutters | Slow USB reads or CPU overload | Overlay: UNDERRUN count, TPS; `fs_smoke` random-read times |
| Picture in black and white / rolling | NTSC signal on a PAL-only display | Different cable or TV (§10) |
| Game slow (TPS below 29.4 in normal rooms) | Hardware slower than PCSX2 | Run the benchmark and send `bench_results.txt` |
| Saves not kept | Writes failing on the stick | `fs_smoke` savedata checks; `savedata/` contents; log errors |

## 8. Retrieving logs and results

Power the console off, then on a PC copy from `VVVVVV/`:
- `fs_smoke.log`;
- `vvvvvv_ps2.log`;
- `bench_results.txt` and `bench_*.csv` / `prof_*.txt` / `golden_*.ppm` (benchmark);
- `savedata/`.

**Timing of the game log.** On real storage it is written by a background thread about every 10 s and at milestones. The newest few seconds before a hard crash can be missing. The fatal and exception screens are designed to make that loss unimportant: the essential information is on screen.

## 9. What to record in the first session

See the checklist in [ps2-hardware-first-boot.md](ps2-hardware-first-boot.md) §5. In short:
- hardware and setup: console model, TV and cable, wLaunchELF version, stick;
- `fs_smoke` result: photo and log;
- start-up: time to title, any stage where it paused;
- picture quality and overscan;
- music and SFX quality by ear: gaps, clicks, pitch;
- overlay values in a normal room and in the Tower;
- the benchmark results file;
- whether saving and loading works.

## 10. Known limitations: what PCSX2 cannot test

| Item | Status |
|---|---|
| USB stick enumeration, bdm/usbmass driver compatibility, `mass:`/`mass0:` naming | **hardware only.** PCSX2 runs from `host:` |
| USB read speed, latency spikes, behaviour if the stick is pulled | **hardware only.** `fs_smoke` measures speed; streaming tolerates stalls up to the 1 s ring |
| FAT32 write/flush/close semantics on a real stick; power loss during a save | **hardware only.** Writes are plain `open`/`write`/`close`, with no explicit sync [C] |
| `remove()` return value | PCSX2 `host:` returns −1 although it deletes; real FAT unknown. `fs_smoke` checks the effect, not the return code |
| Real EE speed (caches) and FPU behaviour | **hardware only.** Compare `bench_results.txt` and golden CRCs |
| SPU2 output quality, clicks, latency | **hardware only** |
| NTSC on a PAL console, CRT overscan | **hardware only.** Output is always NTSC 640×448i |
| libdebug text screens and the overlay on a real TV | Rendered and captured in PCSX2 [M]; on-TV readability unverified |
| Exception screen on real faults | Verified in PCSX2 with a trap [M]. PCSX2 does **not** raise address errors for unaligned accesses, so that class could not be tested |
| Memory card, PAL mode, GS renderer, ADPCM | not implemented (out of scope) |

## 11. Filesystem audit (code review) [C]

| Topic | Finding |
|---|---|
| `mass:` paths | No hard-coded device. The base directory is `getcwd()`; PhysFS mounts `<base>data-ps2.zip`; saves go to `<base>savedata/` |
| Directories | `ps2_mkdir` strips trailing `/` (some IOP drivers reject it) and logs failures |
| Relative vs absolute | Diagnostics (`vvvvvv_ps2.log`, bench files, `fs_smoke.*`) use paths relative to cwd. Game data uses absolute `<base>…` paths |
| Seeking and buffered reads | Assets are read whole at start-up (2.47 MB). Music streams from the stored zip entry through PhysFS with a 32 KB buffer, only on the worker thread. Seek inside a stored entry costs ~0.07 ms in PCSX2 (P2b) |
| Create, flush, close | Game saves (`settings.vvv`, `unlock.vvv`, …) go through PhysFS `openWrite`/`close`. The log rewrites the whole file with `O_TRUNC` |
| Archive access | `data-ps2.zip` is preferred and must have the music blob stored; checked at start with a clear error otherwise (P2b) |
| Slow or interrupted reads | Music worker reads block only that thread; underruns are counted and shown. Start-up asset reads block the main thread, which is expected during loading |

## 12. Validation in PCSX2 (H1 build)

| Check | Result [M] |
|---|---|
| Normal gameplay unchanged | All 10 P3 scenes: **golden frames 10/10 identical** to P3's final run; metrics within noise |
| Gameplay run (new game + walk, 5 min, music on) | render mean 10.16 ms, max period 39.2 ms, **0 underruns**, peak `malloc_in_use` 16.87 MiB (P3: 10.15 ms, 41.9 ms, 0, 16.87 MiB) |
| Overlay on/off | `overlay.txt` on at start; virtual pad **L3+R3** toggled on → off → on (log `OVERLAY on/off`); overhead in §4 |
| Startup diagnostics, missing assets | Package without `data-ps2.zip`: FATAL ERROR screen with the reason, last stage, the error lines, a PS2 hint and the log path; stays up |
| Boot console | All stages up to "starting the renderer" captured on screen (`bootshot.txt`) |
| Exception screen | `crashtest.txt` (trap): register screen + EE serial line + log `EXCEPTION trap code 13 EPC 001fb17c`; `--addr` gives `PS2_LoopEnd+0xae4` (the test trap) |
| `fs_smoke` errors | Package OK → `ALL OK`. One flipped byte inside a checked chunk → `MISMATCH data-ps2.zip @30344172` + failure list. Archive missing → three failures, with a single "cannot open" line |
| Hardware benchmark | Completes unattended and writes `bench_results.txt` (§5) |
| Music | 0 underruns in every run above |
| Memory | Peak 16.87 MiB in gameplay; benchmark runs ~17.2 MiB including the benchmark's buffers; bounded |
| Clean builds reproducible | Two clean builds (SDL from the tarball plus patches 0001–0007, `build-vvvvvv-ps2.sh --refetch`) give the **tested ELFs bit for bit**: `VVVVVV.elf` `04d65cb6ccf7395b…`, `VVVVVV-nomusic.elf` `50edfb112910c005…` |

**Diagnostic code added:**
- `PS2Diag.cpp`, about 540 lines;
- SDL patch 0007, a weak hook with 4 call sites;
- small hooks in `main.cpp`, `Vlogging.c` and `FileSystemUtils.cpp`.

Everything is PS2-only (`__PS2__`). The host build still compiles.

## Build the USB package

```sh
# once: toolchain image and SDL (see docs/ps2-p1-report.md)
scripts/build-sdl2-ps2.sh
# game, fs_smoke, package (uses your own data.zip; never modified)
scripts/make-usb-package.sh ~/path/to/data.zip            # -> build/usb-package/VVVVVV/
# or, for a byte-identical rebuild from pinned sources first:
scripts/build-vvvvvv-ps2.sh --refetch && scripts/make-usb-package.sh ~/path/to/data.zip --no-build
```
